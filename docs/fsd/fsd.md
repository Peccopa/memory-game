# Feature-Sliced Design

Краткая памятка по архитектуре **Feature-Sliced Design (FSD)**.

FSD — это набор правил организации frontend-кода. Главная идея — разделять код по ответственности и предметной области, чтобы проект было проще развивать и поддерживать.

---

## Структура

В проекте используются следующие слои:

```text
src/
├── app/
├── pages/
├── widgets/
├── features/
├── entities/
└── shared/
```

Слой `processes` не используется — он устарел и официально считается deprecated.

Все слои использовать необязательно. Добавляем только те, которые действительно нужны проекту.

---

## Слои

### `app`

Всё, что относится ко всему приложению:

- запуск приложения;
- роутинг;
- глобальные стили;
- глобальное состояние;
- конфигурация;
- провайдеры.

Примеры:

```text
app/
├── routes/
├── store/
├── styles/
└── entrypoint/
```

---

### `pages`

Полноценные страницы приложения.

Например:

```text
pages/
├── home/
├── catalog/
└── profile/
```

Страница может использовать `widgets`, `features`, `entities` и `shared`.

---

### `widgets`

Крупные самостоятельные блоки интерфейса, которые объединяют несколько элементов или функций.

Например:

```text
widgets/
├── header/
├── product-list/
└── shopping-cart/
```

Widget обычно представляет законченную часть интерфейса, но не является полноценной страницей.

---

### `features`

Пользовательские действия и функции, имеющие бизнес-смысл.

Например:

```text
features/
├── auth/
├── add-to-cart/
├── search-product/
└── change-theme/
```

Feature отвечает на вопрос:

> Что пользователь может сделать?

---

### `entities`

Бизнес-сущности приложения.

Например:

```text
entities/
├── user/
├── product/
├── order/
└── cart/
```

Entity отвечает на вопрос:

> С чем работает приложение?

---

### `shared`

Переиспользуемый код, который не относится к конкретной бизнес-сущности.

Например:

```text
shared/
├── ui/
├── api/
├── lib/
└── config/
```

Здесь могут находиться:

- UI-компоненты;
- API-клиент;
- утилиты и библиотеки;
- конфигурация;
- общие стили.

`shared` не должен содержать бизнес-логику конкретного проекта.

---

# Слои → Слайсы → Сегменты

FSD использует три уровня организации:

```text
Layer
  ↓
Slice
  ↓
Segment
```

### Layer

Крупный архитектурный уровень:

```text
features/
```

### Slice

Предметная область внутри слоя:

```text
features/
└── add-to-cart/
```

Название slice определяется самим проектом. Единого списка названий нет.

### Segment

Группировка кода внутри slice по назначению:

```text
features/
└── add-to-cart/
    ├── ui/
    ├── model/
    └── api/
```

Наиболее распространённые сегменты:

| Segment  | Назначение                     |
| -------- | ------------------------------ |
| `ui`     | интерфейс и отображение        |
| `api`    | работа с backend               |
| `model`  | состояние, типы, бизнес-логика |
| `lib`    | внутренние библиотеки          |
| `config` | конфигурация                   |

`components`, `hooks` и `types` как названия сегментов обычно менее полезны, потому что описывают техническую форму кода, а не его назначение.

# Главное правило зависимостей

Код может импортировать код **только с нижележащих слоёв**.

```text
app
 ↓
pages
 ↓
widgets
 ↓
features
 ↓
entities
 ↓
shared
```

Например:

```text
pages → features  ✅
features → entities  ✅
entities → shared  ✅

features → pages  ❌
entities → features  ❌
```

Слайсы одного слоя также не должны напрямую зависеть друг от друга.

---

# Public API

Внешний код не должен обращаться к внутренней структуре slice напрямую.

Вместо:

```ts
import { Button } from '@/shared/ui/button/Button';
```

предпочтительно использовать публичный API:

```ts
import { Button } from '@/shared/ui/button';
```

Обычно для этого используется `index.ts`.

Это позволяет менять внутреннюю структуру slice, не ломая внешний код.

---

# Главное

При добавлении нового кода сначала задаём вопрос:

1. **К какому уровню ответственности он относится?**
2. **Есть ли у него бизнес-сущность?**
3. **Это пользовательское действие?**
4. **Это крупный UI-блок?**
5. **Это целая страница?**
6. **Или это общий код?**

Не нужно создавать все возможные папки заранее.

**FSD — не про большое количество папок. FSD — про понятные границы ответственности.**
